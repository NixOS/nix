# Version 1 derivation "ATerm" format

This is the form of [version 1] derivations in the [derivation "ATerm" format](../derivation-aterm.md), whose [common productions](../derivation-aterm.md#common) it uses.

```ebnf
derivation-v1 = "Derive(" outputs-v1 "," input-drvs-v1 "," input-srcs ","
                platform "," builder "," args "," env-v1 ")" ;

outputs-v1    = list(output-v1) ;
output-v1     = "(" output-name "," output-fields ")" ;

input-drvs-v1 = list(input-drv-v1) ;
input-drv-v1  = "(" drv-path "," output-names ")" ;

env-v1        = list(env-entry-v1) ;
env-entry-v1  = "(" string "," string ")" ;
```

Each input derivation entry pairs the store path of an input derivation with the outputs of it that are used; at least one output must be named.

[Options](@docroot@/store/derivation/index.md#options), *pass as file* flags and [structured attributes](@docroot@/store/derivation/index.md#structured-attrs) are all encoded in the environment variables, so the grammar has nothing for them.

One exception is known.
The JSON held in the [`__json` environment variable](@docroot@/store/derivation/index.md#structured-attrs) of a version 1 derivation using structured attributes is *not* required to be canonical JSON.
It must instead be preserved verbatim rather than reserialised.
Since the bytes are hashed, whatever encoding a derivation happens to carry is part of its identity.
Re-emitting it — even as equivalent JSON — would change the derivation.

> **Note**
>
> This is not because canonicity is unwanted here, but because there is no settled notion of it to require.
> "Canonical JSON" has several competing definitions, disagreeing on key ordering, number representation, and Unicode escaping.
> It is also technically fraught:
> for example, without hex literals for floating point, number representation is barely tractable.
> Structured attributes have been in the wild for many years, so any such choice would also have to reckon with the encodings already out there.
> Committing to one of them is therefore not a choice we are yet in a position to make with this format.

## Masked derivations {#input-address-encoding}

An [input-addressed](@docroot@/store/derivation/outputs/input-address.md) output path of a [version 1] derivation is computed by hashing the ATerm representation of a derivation that has been [masked](@docroot@/store/derivation/outputs/input-address.md#input-masked-drv) first: parts of it are blanked out before hashing, so that derivations differing only in what was blanked hash alike.
[Version 2] derivations are not masked.

Their encoding differs from the grammar above in one production:

```ebnf
input-drv-v1 = "(" drv-hash "," output-names ")" ;
drv-hash     = verbatim ;   (* lowercase hexadecimal *)
```

That is, an `inputDrvs` key is a hash rather than a store path.

See [input addressing](@docroot@/store/derivation/outputs/input-address.md#input-masked-drv) for how those hashes are derived and why; in short, they identify an input derivation up to what it produces rather than how, so that changing where a fixed-output input is fetched from does not change anything downstream.

Replacing the input derivation paths with hashes like this is *input masking*, and is performed on all version 1 derivations.

Whether the outputs carry their paths depends on what is being hashed.
When computing a derivation's own output paths they are *output masked* too — `output-path`, and the environment variable named after each output, are empty — since those paths are what is being computed; the result is *fully masked*.
When hashing a derivation to stand in for it as an *input* to another, they are left as they are, and the result is *input-masked* only.

The result is not a derivation that can be built or written to the store: its inputs name hashes, not paths.
It exists only to be hashed.
